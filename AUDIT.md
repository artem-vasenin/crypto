# AUDIT.md — аудит исходного проекта

## Итог

Исходный проект выглядел как уже готовый торговый бот, но на самом деле в execution-части были несколько критических ошибок. Самая опасная группа — ошибки вокруг lifecycle заявки, позиции и защитных ордеров.

Я разделяю проблемы на:

- **CRITICAL** — могли привести к отсутствию сделки, неверному состоянию или реальному денежному риску;
- **HIGH** — серьёзно ухудшали корректность;
- **MEDIUM** — архитектурные/исследовательские проблемы;
- **LOW** — качество кода.

---

# CRITICAL

## 1. PostOnly выставлялся на неправильной стороне стакана

**Исходник:** `internal/execution/engine.go`

Для long:

```text
entryPrice = ask
```

Для short:

```text
entryPrice = bid
```

Для `PostOnly` это практически перевёрнутая логика.

Buy по ask стремится забрать уже существующую ликвидность. Sell по bid делает то же самое в обратную сторону. Bybit специально отменяет PostOnly-заявку, если она при отправке должна исполниться как taker.

**Исправление:**

- Buy → bid;
- Sell → ask;
- цена дополнительно округляется в правильную сторону.

---

## 2. Бот считал заявку открытой позицией сразу после `order/create`

Исходный код создавал `PositionState` ещё до фактического fill.

Затем после успешного ответа `order/create` локальное состояние становилось полноценной позицией.

Проблема:

```text
order created
      ↓
локально "позиция открыта"
      ↓
заявка может вообще не исполниться
      ↓
бот блокирует символ
```

Для PostOnly это особенно плохо, потому что заявка может долго стоять в стакане или быть отменена.

**Исправление:**

Введено состояние `Pending`.

Теперь:

```text
PENDING ORDER
     │
     ├── Filled → POSITION
     ├── PartiallyFilled → POSITION state from position WS
     ├── Cancelled → remove pending
     └── Rejected → remove pending
```

---

## 3. Не было нормального order lifecycle

Исходный бот не отслеживал реальный `orderStatus`.

Он мог получить `orderId`, но дальше не контролировал:

- New;
- PartiallyFilled;
- Filled;
- Cancelled;
- Rejected.

**Исправление:**

Private WebSocket теперь подписан на `order`.

Добавлена обработка lifecycle.

---

## 4. После рестарта локальное состояние не соответствовало Bybit

Исходный `Engine` начинал практически с пустых maps:

```text
positions = {}
```

Если на Bybit уже была позиция, бот мог её не учитывать.

**Исправление:**

При старте:

```text
wallet balance
      +
position/list
      +
order/realtime
```

синхронизируются с локальным состоянием.

---

## 5. `MaxTotalMarginUSD` фактически не использовался

Параметр был в конфиге:

```json
"max_total_margin_usd": 12
```

но реального контроля общей зарезервированной маржи не было.

Контролировались только:

- balance;
- max active positions.

**Исправление:**

Перед новой заявкой считается:

```text
reserved margin of active/pending positions
+
new trade margin
```

и сравнивается с `MaxTotalMarginUSD`.

---

## 6. Использовался устаревший `availableToWithdraw`

Для Unified Account это поле deprecated.

Вместо него для cross/portfolio margin следует использовать `totalAvailableBalance`.

**Исправление:**

Бот теперь использует:

```text
totalAvailableBalance
```

и WebSocket wallet также читает account-level доступный баланс.

---

## 7. `switch-isolated` находился в торговом пути

Исходник пытался вызвать:

```text
/v5/position/switch-isolated
```

Это особенно проблемно для UTA 2.0: endpoint для переключения cross/isolated там не поддерживается.

Ещё хуже — ошибки этого вызова игнорировались.

**Исправление:**

Вызов полностью убран из execution path.

---

## 8. SL мог рассчитываться около нуля

Исходный алгоритм:

```text
pivotDistance = entryPrice - pivotLevel
actualDistance = max(pivotDistance, minDistance)
SL = entryPrice - actualDistance
```

Если `pivotLevel == 0`, long мог получить:

```text
pivotDistance = entryPrice
```

и SL фактически уходил к нулю.

Это не нормальный fallback.

**Исправление:**

Если pivot отсутствует:

```text
SL distance = ATR * multiplier
```

Pivot используется только если он находится на правильной стороне цены.

---

## 9. Защитные уровни могли не пройти проверку уже после входа

Исходный поток:

```text
place order
   ↓
fill
   ↓
calculate SL/TP
   ↓
try SetTradingStop
```

Если расчёт SL/TP невалиден, позиция уже существует.

**Исправление:**

Теперь есть:

```text
pre-trade risk calculation
        ↓
SL valid?
TP valid?
costs acceptable?
        ↓
только потом order/create
```

Кроме того, SL/TP передаются уже при создании заявки.

---

## 10. `SetTradingStop` не указывал `tpslMode`

В актуальном API `tpslMode` является обязательным параметром.

**Исправление:**

Для full-position TP/SL используется:

```text
tpslMode = Full
positionIdx = 0
tpOrderType = Market
slOrderType = Market
```

---

## 11. Grid strategies существовали в коде, но не были зарегистрированы

В проекте были:

- `long_grid.go`;
- `short_grid.go`;
- `neutral_grid.go`.

Но `strategies.Names()` возвращал только:

```text
long
short
```

а `strategies.New()` не создавал grid strategies.

То есть часть кода фактически была мёртвой.

**Исправление:**

Все пять стратегий зарегистрированы.

---

## 12. Grid strategy могла быть случайно превращена ботом в directional trade

Это ещё опаснее.

Если передать:

```text
-strategy long-grid
```

старый execution engine определял side через:

```text
если не long → Sell
```

То есть grid strategy потенциально превращалась в short.

**Исправление:**

Execution bot принимает только:

```text
long
short
```

Grid стратегии являются screening-only.

---

# HIGH

## 13. WebSocket universe фиксировался только на первом запуске

Исходный screener:

```text
first run:
Top 60 → subscribe
```

Дальше список подписок не обновлялся.

Если монета вышла из Top 60, а другая вошла, новая монета могла остаться без WS history/order book.

**Исправление:**

Каждый screening cycle новые символы добавляются через `AddSymbols()`.

Для новых символов выполняется REST warmup.

---

## 14. Анализировалcя формирующийся candle

WS обновляет текущую свечу.

Исходный код передавал её непосредственно в:

- RSI;
- ATR;
- structure;
- change calculations.

В результате score мог резко меняться внутри свечи.

**Исправление:**

Перед анализом последняя свеча удаляется.

Скриннер использует только закрытые свечи.

---

## 15. Order book не имел проверки свежести

Старый cache мог содержать старый стакан.

При disconnect WebSocket данные могли оставаться в памяти, а стратегия продолжала считать imbalance.

**Исправление:**

Для каждого стакана хранится `updatedAt`.

Кандидат допускается только при свежем snapshot.

---

## 16. VolumeRatio содержал off-by-one

Исходный код исключал последнюю свечу, но затем рассчитывал среднее количество предыдущих свечей с неверным количеством элементов.

Фактически denominator был `period`, а элементов в сумме было на один меньше.

**Исправление:**

Берутся ровно `period` завершённых предыдущих свечей.

---

## 17. Quantity мог молча увеличиваться ради minNotional

Исходный код:

```text
if targetNotional < minNotional:
    увеличить quantity
```

Это значит:

```text
запланировано $6
биржа требует $10
бот отправляет $10
```

То есть нарушается собственный risk budget.

**Исправление:**

Если configured margin недостаточна для exchange minimum — сделка отклоняется.

---

## 18. Ошибки `setTradeModeIsolated` и `setLeverage` обрабатывались неодинаково

Исходный код игнорировал ошибки:

```text
_ = setTradeModeIsolated(...)
_ = setLeverage(...)
```

В результате бот мог продолжить работу с неожиданным leverage/margin mode.

**Исправление:**

Leverage теперь является обязательным этапом.

Неожиданный ответ — отказ от сделки.

---

# MEDIUM

## 19. `max_price` — слабый универсальный фильтр качества

Фильтр:

```text
price <= 50
```

ничего сам по себе не говорит о качестве монеты.

Цена токена $0.10 не делает его дешевле BTC с точки зрения риска.

Этот фильтр можно использовать как осознанное ограничение universe, но нельзя трактовать как quality filter.

В исправленной версии он оставлен как конфигурационный фильтр, потому что это уже исследовательское решение, а не программная ошибка.

---

## 20. `max_grid_spread_pct` применяется не только grid strategy

Название параметра предполагает grid, но spread-фильтр применяется до выбора стратегии.

То есть он влияет также на long/short.

Это не обязательно плохо, но название вводит в заблуждение.

---

## 21. OI expansion > 0.05% используется как жёсткий gate и для long, и для short

Это слишком грубая модель.

Рост OI сам по себе не говорит:

```text
bullish
```

или:

```text
bearish
```

Он говорит только, что в рынок добавляется открытый интерес.

Направление надо связывать с движением цены, funding, ликвидациями и контекстом.

В этой версии это не переписано полностью, потому что это уже изменение торговой гипотезы, а не очевидный bug.

---

## 22. Order-book imbalance по top-10 не является надёжным сигналом

Даже при локальном стакане остаются проблемы:

- spoofing;
- отмена крупных ордеров;
- отсутствие временной устойчивости;
- отсутствие нормализации по расстоянию от mid-price.

В проекте imbalance разумнее использовать как подтверждающий фактор, а не как самостоятельный прогноз.

---

## 23. Support/resistance строится только из простых pivot

Это удобный baseline, но не полноценная модель уровней.

Нет:
- кластеризации близких pivot;
- volume-at-level;
- количества касаний;
- возраста уровня;
- силы реакции от уровня.

---

## 24. ATR4h, некоторые поля Indicators и BTC trend не участвуют в текущем score

В модели присутствуют:

```text
ATR4h
PriceVsEMA10_15m
BTC15mTrendPct
```

часть которых не используется стратегиями.

Это не bug, но создаёт иллюзию большей сложности анализа, чем реально используется.

---

# LOW

## 25. В исходном архиве были `.DS_Store`

Это macOS metadata.

Из исправленного архива они удалены.

---

## 26. `FundingAvg` и `FundingAvg24h` фактически дублировали друг друга

В исходном коде:

```text
FundingAvg = FundingAvg24h
```

Это лишнее поле.

Оставлено ради совместимости JSON, но дальше его лучше удалить после изменения downstream consumers.

Проверена структура всего исходного ZIP.

Всего в исходном архиве было 36 файлов, включая два `.DS_Store`.

Отдельно проверены:

- strategies;
- indicators;
- structure;

# Важное замечание о тестировании

В текущем рабочем окружении доступен Go 1.23.2, а проект требует Go 1.26.5. Кроме того, окружение не имеет сетевого доступа к `proxy.golang.org`.

Поэтому выполнить реальный `go test ./...` на Go 1.26.5 с настоящими внешними модулями здесь невозможно.

Вместо этого выполнена:

```text
gofmt
go test ./...
go vet ./...
```

на копии проекта с локальными compile-time заглушками внешних пакетов.

Результат:

```text
go test ./...   PASS
go vet ./...    PASS
```

Это подтверждает синтаксис, типы и внутреннюю согласованность проекта, но **не является заменой запуска на реальном Go 1.26.5 с настоящим gorilla/websocket и реальным Bybit**.

Перед mainnet обязательна Testnet-проверка.
